# 대화 프롬프트와 백엔드 맥락

`feature/system-prompt`의 로컬 구현. 원격 DB 마이그레이션·개발 배포·야간 cron 활성화는 이 커밋으로 자동 수행되지 않는다.

## 대화 모델에 전달하는 것

사용자가 제공한 전문은 `src/lib/companion-prompt.ts`의 `SYSTEM_PROMPT`에 그대로 두고 줄바꿈만 정리했다. 기존 온보딩 한 문장 지시는 교체했다. 이후 사용자 요청으로 “매 답변은 제공된 사용자 페르소나, 관련 기억, 대화 요약, 최근 대화를 바탕으로 작성한다. 이 정보를 매번 언급할 필요는 없다.”를 대화 원칙에 추가했다. 글·Live·Live 위임이 같은 템플릿을 사용한다. 음성 세션 시작에는 별도의 developer 메시지 `사용자가 먼저 말하기를 기다리지 말고, 지금 바로 한국어로 짧게 인사하세요. 인사한 뒤에는 사용자의 말을 기다리세요.`를 보낸다. 하품 애니메이션은 연결과 동시에 진행하며 네트워크 연결을 지연하지 않는다.

| 자리 | 서버가 채우는 값 |
| --- | --- |
| here_name | 인증된 계정의 `here_profile_v1.profile.companion`, 없으면 기존 기본 이름 호야 |
| character_scaffold | 빈 문자열. 별도 성격 설정을 받지 않았으므로 예전 스타일에서 만들지 않음 |
| user_persona | 백엔드에 저장된 네 온보딩 질문·응답 JSON. 빠진 답은 추측하지 않음 |
| retrieved_memories | 검색 결과 최대 5개의 요약·시각 JSON |
| chat_summary | DB 누적 요약, 없으면 빈 문자열 |
| recent_messages | 검증한 최근 대화 메시지 JSON. Responses의 input에도 같은 대화를 전달 |
| app_signals | 실제 대화 경로 `conversation_mode: chat 또는 voice` |
| tone_guidance | 백엔드가 이번 사용자 메시지까지의 감정 흐름으로 만든 다음 답변의 톤 안내 |

인증 서버에서 읽은 이름·온보딩 데이터만 사용한다. 요청 본문의 이름·프롬프트·기억·톤으로 이를 덮어쓸 수 없다. 템플릿은 한 번만 치환해 데이터 안의 `{{...}}`를 다시 해석하지 않는다.

## 답변 전 처리

- 기존 `MEMORY_ENABLED` 개발 제한과 최신 대화 저장 동의를 따른다. 운영에서는 비활성이다.
- DB의 접근 revision을 확인하고 시작한다. `0021`이 없거나 동의·접근 확인이 실패하면 추가 답변 모델 호출 없이 503으로 종료한다. 정상 조회 결과가 빈 계정은 대화할 수 있다.
- 최신 메시지의 벡터 검색, 누적 요약 읽기, 감정 흐름·검색용 후속 질문 생성을 병렬로 시작한다.
- 분석 모델은 기존 `MEMORY_SUMMARY_MODEL`(기본 Luna)을 재사용한다. 분석 입력은 최근 8개 발언, 각 최대 2,000자다. 톤은 240자 이내이고 사용자 원문 근거가 없는 출력은 버린다. 고정 캐릭터 성격은 생성하지 않는다.
- 후속 질문 최대 2개도 별도로 임베딩해 본인 벡터 DB를 검색한다. 직접 검색 결과를 우선하고 ID 중복을 제거해 최대 5개를 선택한다.
- 실제 글·음성 경로의 처리 제한은 4.5초다. 직접 기억 검색과 DB 요약 읽기는 필수이며 실패하면 맥락 없이 답변하지 않고 503을 반환한다. 톤 분석·추가 검색 질문 실패는 필수 조회 성공분을 유지한다. 마지막 접근 확인에는 최대 1초를 사용한다. 동의 철회·기억 삭제·요약 revision 변경이 감지되면 답변을 중단한다. 이 수치는 설정된 제한이며 실측 응답 속도가 아니다.
- 글 대화와 Live 위임은 결과를 받은 뒤 템플릿에 반영한다. Live 시작 전에는 `read_live_context()`로 본인 요약·최근 기억 5개·최근 원문 8개를 읽어 초기 프롬프트부터 전달한다. 원문은 시작 프롬프트에서 발언당 마지막 1,000자로 제한한다. 조회 실패 시 Live 세션을 만들지 않는다.
- Live 자체는 사용자 발화 조각이 도착하면 재생을 음소거하고 기다리도록 지시한다. 조각이 400ms 동안 추가되지 않을 때 `/api/live/context`를 요청한다. 모든 `session.thinking.append` 조각의 ACK를 받은 뒤, 실제 원격 오디오가 250ms 동안 조용한 경계를 확인하고 최신 맥락으로 답변하도록 지시하며 재생을 재개한다. 음소거 중에도 스트림을 재생해 이전 음성을 버리며, 그 전사는 대화 기록에 저장하지 않는다. 새 사용자 조각·통화 종료 뒤 늦은 결과는 버린다. 위임 답변이 재생 재개보다 먼저 도착하면 보관했다가 맥락 적용 후 전달한다. 기다리는 사이 새 발언이 오면 해당 답변도 폐기하고 다시 생성한다.
- ACK만으로 재생을 재개하지 않는다. 전달/무음 경계 확인이 8초 안에 끝나지 않거나 맥락 조회가 실패하면 소리를 재개하지 않고 세션을 종료해 재연결을 안내한다. 사용자가 소리를 꺼 둔 상태는 맥락 갱신으로 해제하지 않는다. 사용자 전사가 도착하기 전 이미 들린 소리를 되돌릴 수는 없으며, 모델의 의미적 반영은 생성 결과다. Live 위임은 별도로 분석하므로 두 경로가 같은 메시지를 분석할 수 있다.

## 답변 후 처리

기존 사용자 사실 추출·대화 구간 요약·임베딩을 유지한다. 대화 저장 후에는 새 백엔드 작업자가 비슷한 기억을 묶고 누적 요약을 갱신한다. 인증된 접속의 작업은 계정별 최대 5분에 한 번, 한번에 대화 배치 2개·새 기억 10개와 각 기억의 가까운 이웃 2개(중복 제거 후 최대 30개)를 다룬다. 여러 호출이 들어와도 동일 계정에는 진행 중인 작업 하나만 허용한다.

- 압축: 비슷한 사실의 중복을 합치고 나머지 원본 행은 삭제 상태로 남긴다. 묶음의 원본→대표 행 관계를 보관한다.
- 모순: 명확한 정정은 정정된 내용을 유지하고, 불명확한 충돌은 시점·귀속을 구분해 보존하도록 분석 모델에 지시한다. 최신 저장 시각만으로 사실의 진위를 결정하지 않는다.
- 누적 요약: 이전 요약+아직 처리하지 않은 저장 대화 배치를 다시 요약한다. 처리한 batch ID를 기록하므로 재전송·다른 탭으로 같은 대화를 중복 요약하지 않는다. 새 대화가 없으면 요약은 유지한다.
- 원본 사용자 삭제: 병합된 자식 기억까지 삭제하고 누적 요약을 비우며 진행 중 작업을 무효화한다. 동의 철회도 누적 요약·작업을 삭제한다. 다른 계정의 데이터는 읽거나 변경할 수 없다.
- 모델의 병합·모순 판단은 자동화된 의미 판단이다. 합성 입력/DB 검사는 통과 여부를 확인하지만 실제 대화의 모든 판단 정확성을 보장하는 시험은 아니다.

## 매일 밤 처리

`0022`의 Supabase cron은 한국 시간 03:00–05:55에 5분 간격으로 최대 2개 작업을 발급한다. 계정별로 아직 그날 밤 검토하지 않은 기억과 미처리 대화 배치를 순차 처리한다. 실패·만료는 계정당 하루 최대 3회까지이며, 야간 실행 창의 처리 용량을 넘는 잔여 작업은 다음 실행 창으로 남는다. 원문·관리자 키를 HTTP 요청에 넣지 않고 2분짜리 단일 작업 토큰만 전달한다.

야간 삭제 기준은 사용자가 선택한 **인사·맞장구 등 새 정보가 없는 기억만**이다. 오래됐거나 검색 빈도가 낮다는 이유로 삭제하지 않는다. 새로운 사실이 섞인 기억은 통째로 지우지 않는다. 낮 동안 병합 작업은 이 삭제 동작을 수행할 수 없다.

## 활성화

1. 기존 `0018`·`0019` 적용 상태를 먼저 확인한다. 기존 수동 migration 이력을 확인하지 않고 일괄 `db push`하지 않는다.
2. 개발 DB에 `0021_conversation_context.sql`과 `0023_live_context_snapshot.sql` 적용.
3. 새 코드의 개발 배포 및 `MEMORY_ENABLED=true` 확인.
4. 개발 DB에 `0022_context_worker_cron.sql` 적용. 고정 개발 URL의 worker 배포가 먼저여야 한다.
5. 합성 계정으로 글·Live 모델 호출, 저장·검색·압축·철회 및 cron 실행 확인.

로컬 자동 검증은 모의 제공자와 PGlite/pgvector를 사용한다. 원격 실제 계정이나 기억 데이터를 수정하지 않는다.

## 이번 변경의 검증

- 실제 Runyour GPT-5.6-sol을 글·음성 위임 모드로 각각 호출했다. 합성 사용자 기억에만 넣은 모임 이름을 두 답변이 모두 회상했다. 실제 사용자 데이터는 사용하지 않았다.
- 실제 Chrome WebRTC → GPT-Live 연결에 합성 음성을 입력했다. 초기 사용자 맥락, 사용자 발화 전사, 맥락 조회·전달 ACK, 음성 답변 전사, 정상 종료를 확인했다. 기억에만 넣은 모임 이름이 최종 답변 전사에 포함됐고 연결 오류는 없었다. 이 시험의 데이터 저장소는 합성 대체 저장소이며 실제 개발 DB 종단 검증과 구분한다.
- 단위 테스트는 전달 ACK만 받은 경우의 재생 차단, 이전 음성 정리, 새 발화·종료 시 늦은 결과 무효화, 오류 시 답변 생성 차단을 검사한다. PGlite 검사는 계정 격리·동의·삭제·시작 맥락 RPC를 검사한다.

관리 토큰 방식의 적용은 `node scripts/activate-development-context.mts`로 현재 상태를 먼저 확인하고, `--apply`로 개발 DB에 누락된 `0018`·`0021`·`0023`만 적용한다. 모든 확인이 끝나면 무시되는 `.env.development.local`의 `MEMORY_ENABLED`를 true로 설정한다. 토큰은 `SUPABASE_ACCESS_TOKEN` 환경변수로 받고 출력하지 않는다. 운영·cron·원격 배포 설정은 이 명령으로 변경하지 않는다.

음성 재생 제어는 [OpenAI 재생 제어 문서](https://developers.openai.com/api/docs/guides/voice-server-controls?api=live#control-playback-when-needed)의 ACK와 실제 재생 구분을 따른다.

## 개발 DB 적용 기록 (2026-11-21)

Supabase CLI 로그인 후 `here-dev` (`mwjwfumpxdlllikcdvkh`)에 누락된 `0018`, `0021`, `0023`을 파일별로 적용하고 PostgREST 스키마를 갱신했다. 로컬의 무시된 `.env.development.local`에는 `MEMORY_ENABLED=true`를 설정했다. CLI 인증은 로컬에 보관하며 저장소에 토큰을 추가하지 않았다.

실제 개발 DB의 트랜잭션 안에서 합성 계정 두 개로 저장·조회·누적 요약·Live 시작 맥락·계정 격리·기억 삭제·동의 철회를 확인한 뒤 전체 롤백했다. 기존 사용자 데이터는 이 검사에 사용하지 않았다. 인증 계정의 Live 조회 함수 실행 권한과 익명 접근 차단도 확인했다.

별도의 실제 GPT-Live WebRTC 시험에서는 사용자 발화 전 인사 오디오와, 합성 저장소의 모임 이름을 반영한 후속 답변을 확인했다. 이 모델 시험은 실제 DB 트랜잭션 검사와 별개다.

원격 앱 환경변수·배포 및 `0019`/`0022` 야간 cron은 이번 로컬 활성화에 포함하지 않았다. 고정 개발 URL에 해당 worker 코드가 배포된 뒤 cron을 적용해야 한다.
