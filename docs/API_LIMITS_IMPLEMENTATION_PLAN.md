## 구현 순서와 완료 기준

### 1. 정책 계약과 서버 종료 방식 확정

- 사용자 결정으로 차감 범위·사전 연결·모델·옛 경로·집계 전환 기준을 확정함.
- 이용 한도와 급격한 반복 요청을 막는 보호 한도를 구분함. 기존 보호 한도는 목적에 맞게 유지하며 사용자에게 표시하는 40회와 분리함.
- 날짜·월 경계는 서버/DB의 `Asia/Seoul` 기준으로 계산함. 브라우저 시간이나 시간대 설정을 신뢰하지 않음.
- 정상 응답의 기준은 서버가 유효한 답변을 완성한 시점으로 제안함. 제공자 실패·빈 응답·검증 오류는 차감하지 않음. 응답 전송 중 네트워크 단절은 클라이언트 표시 여부를 서버가 확정할 수 없으므로 요청 ID와 재조회/중복 방지 계약을 함께 설계함.
- 음성의 연결 시작·종료를 서버에서 관측하는 방식을 먼저 검증함. 한도는 연결 경과 시간이며 제공자의 요금 계산과 별개임.

**서버 종료의 기술 선행 조건**

공식 API는 서버 sideband 연결을 통한 `session.close`를 제공함. REST `POST /live/sessions/{session_id}/hangup`은 상세 레퍼런스에 SIP용이라고 기재돼 있어 WebRTC 종료 지원을 가정하지 않음. 임의 만료 시간을 세션 생성 옵션으로 지정하는 필드는 확인되지 않았고, 응답의 `expires_at`은 읽기 값임. 필드를 추정해서 구현하지 않음.

- 서버가 공급자 세션 ID를 계정·앱 통화 ID와 연결해 저장하고, 서버 소유 종료 기한과 종료 작업을 관리함.
- 브라우저가 백그라운드로 가거나 닫혀도 종료 작업이 실행되어야 함. HTTP 응답 이후의 단순 타이머나 클라이언트 heartbeat만으로 강제 종료를 보장하지 않음.
- 현재 배포에서 실행 가능한 지속 작업/스케줄러 또는 공급자 만료 기능을 검증해 선택함. 별도 인프라나 비용이 필요한 경우 구체적인 구성과 비용을 확인한 뒤 사용자에게 결정 요청함.
- 종료 실행이 준비되지 않으면 새 유료 통화를 열지 않음. 종료 요청 실패 시 재시도·운영 확인 상태를 남기고, 기존 통화가 살아 있을 수 있는 상태에서 동시 통화 잠금을 해제하지 않음.
- 공급자 종료 API 성공과 실제 종료 확인을 구분해 기록함. 실제 강제 종료 검증 전에는 음성 한도 적용 완료로 표시하지 않음.

근거: [Live 세션 API](https://developers.openai.com/api/reference/typescript/resources/live/subresources/sessions), [서버 제어](https://developers.openai.com/api/docs/guides/voice-server-controls), [종료와 사용량](https://developers.openai.com/api/docs/guides/live-conversations#usage-and-graceful-close).

### 2. DB 집계와 동시성 제어

- 기존 마이그레이션을 수정하지 않고 새 마이그레이션을 추가함. 적용 직전 최신 dev와 번호 충돌을 확인함.
- 텍스트: 계정·한국 날짜별 완료 수와 진행 중 예약을 관리함. 요청 전에 자리를 예약하고 정상 완료 시 확정, 실패 시 해제함. 동시 요청으로 40회를 넘기지 않도록 DB에서 원자적으로 처리함.
- 동일 예약의 완료 재시도는 중복 차감하지 않음. HTTP 재전송에 답변을 재생하는 기능은 별도이며, 현재 구현은 새 답변이 정상 생성되면 새 1회로 집계함. 프로세스 중단으로 남은 예약은 안전하게 정리하며 이미 발생한 성공을 무조건 실패로 환급하지 않음.
- 음성: 계정당 활성 통화 하나만 허용하고, 1회·당일 잔여·당월 잔여 중 가장 짧은 시간으로 통화 상한을 계산함. 정상 종료는 실제 연결 시간으로 정산하고 잔여 예약을 반환함.
- 자정/월말을 지나는 통화는 해당 기간별 초를 분리해 계산함. 단순히 다음 날 한도를 미리 소진하거나, 월 경계에서 기존 사용량을 중복 정산하지 않음.
- 계정 인증·탈퇴 상태·동의 확인과 기존 데이터 접근 권한을 유지함. 사용자가 집계·세션 소유권·기한·성공 상태를 직접 조작할 수 없게 함.
- 사용량 기록에는 대화 원문·음성 파일을 추가하지 않음. 메타데이터 보관·정리 방식은 기존 계정 삭제 정책과 맞춤.

### 3. API와 음성 수명 관리

- `/api/chat`: 요청 검증 → 보호 한도/이용 한도 예약 → 답변 생성 → 성공 차감 확정 또는 실패 해제.
- 검색·리포트·음성 위임: 결정된 부가 호출 정책으로 분리함. 음성 위임은 본인 활성 통화에 연결하고 종료된 통화의 추가 호출을 막음.
- `/api/live`: 동시 통화 확인 → 시간 예약 → 공급자 연결 → 서버 종료 예약/관측 → 클라이언트 응답. 중간 실패로 유료 세션만 남지 않도록 보상 처리함.
- 수동 종료·한도 종료·연결 실패·중복 종료를 같은 정산 계약으로 처리함. 클라이언트가 보낸 시간이나 사용량을 최종 진실로 사용하지 않음.
- `/api/quota`: 글 남은 횟수, 음성 당일/당월 남은 초, 초기화 시각을 서버에서 반환함. 월 한도 오류의 대기 시간이 하루보다 길 수 있으므로 현재 retry_after 검증도 변경함.
- 옛 `/api/realtime` 처리 방침을 반영해 우회 경로를 없앰.

### 4. 제품 화면

- 메뉴에 글 남은 횟수와 음성 당일/당월 남은 시간을 표시함. 기존 간격·아이콘·공통 스타일은 유지하고 필요한 정보 구획만 추가함.
- 통화 시작 전 이용 가능한 시간, 통화 중 남은 시간, 종료 이유를 구분함.
- 음성 한도 도달 후 글 대화로 이어갈 수 있게 함. 글 한도와 음성 한도는 독립적으로 안내함.
- 한도 초과, 분당 보호 제한, 서비스 장애, 공급자 잔액 부족 메시지를 구분함.
- 마이크를 눌렀을 때만 연결하고, 통화 중 대기 시간을 차감함. 종료 시 마이크·재생을 즉시 중지하고 공급자 종료 이벤트를 수신한 뒤 연결을 정리함. 홈 복귀·화면 재표시로 자동 재연결하지 않음.

## 현재 산출물

- 글 정상 답변 40회/KST 날짜, 원자적 예약·성공 정산·실패 해제, 별도 부가 호출 보호 한도, 메뉴 조회, 옛 음성 API 410.
- 음성 300초/회·600초/일·1800초/월, 계정당 활성 1통화, 공급자 생성 전에 서버 예약, 감시 연결 준비 후 SDP 반환. 수동 종료 API와 음성 위임·맥락 요청의 활성 통화 확인.
- DB 관측 구간을 KST 일·월로 나누어 집계. 종료 확인 전에는 재연결을 허용하지 않고, 기한 초과도 집계한다. 공급자 보고 사용량은 별도 보관한다.
- 감시 API는 작업 claim 후 202로 응답하고 Next.js after 실행 안에서 감시한다. 짧은 작업 간 연결을 검증한 뒤 인계하며, 인계 실패는 기존 감시 연결로 먼저 종료한다.
- 개발 DB에 0031–0037 적용. 0030은 다른 작업의 암호화 변경이므로 텍스트 한도는 0034로 번호를 분리했다. 기존 데이터·6개 예약 작업은 유지하고 음성 감시 작업만 추가했다.

## 개발 반영 및 복구 순서

1. PR의 테스트/리뷰 후 dev 배포 준비 시 새 음성 발급을 일시 중지한다. 활성 통화 0을 확인한다.
2. dev Preview에 등록한 서버 authority 비밀값과 활성화 변수 2개를 확인하고 새 코드를 배포한다. 기존 암호화 키는 교체하지 않는다.
3. DB 감시 endpoint를 해당 dev 배포로 바꾸고, 공급자 연결·종료 확인과 사용량 조회를 확인한 뒤 발급을 켠다. 발급은 dispatch가 꺼져 있으면 유료 공급자 호출 전에 거절한다.
4. 되돌릴 때는 새 발급 중지→기존 통화의 종료 확인→활성 레코드 0→감시 비활성화 순서다. 종료가 불확실한 레코드를 임의 해제하지 않는다.
5. 운영 DB/main 적용은 별도 승인 대상이다. 브라우저 중단/백그라운드, 두 실제 기기 동시 연결, 일·월 잔여가 더 짧은 실제 통화는 후속 검증 항목이다. DB 테스트와 실제 공급자 시험 범위를 섞지 않는다.
