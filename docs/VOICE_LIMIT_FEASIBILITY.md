# Vercel·Supabase 음성 한도 사전 검증

2026-11-28. `feat/api-rate-limit`. 제품 음성 정책은 아직 미적용.

## 현재 계정에서 확인한 사실

| 대상 | 확인 결과 | 확인 방식 |
| --- | --- | --- |
| Vercel Here 팀 | Hobby, active | 로그인된 CLI의 팀 API |
| Vercel here 프로젝트 | Fluid Compute 사용, Node.js 24 | 프로젝트 API |
| Supabase here-dev | Free, Seoul, Nano | 로그인된 개발 프로젝트 대시보드 |
| DB 예약 실행 | pg_cron 1.6.4, pg_net 0.20.4 설치 | 개발 DB 읽기 전용 SQL |
| 기존 예약 작업 | 6개 활성 작업, 기존 conversation-worker 포함 | cron.job에서 이름·주기·활성 여부만 조회 |

초기 조회에서는 요금제·권한·프로젝트 설정·기존 cron·배포 DB 스키마를 변경하지 않았다. 이후 개발 DB 적용 상태는 아래 후속 검증 항목에 기록한다. CLI로 받은 Preview 환경파일의 비밀 변수는 값이 비어 있어 로컬 개발키와 동일한지 확인할 수 없었다. 임시 환경파일은 검증 후 삭제했다.

## 공식 제약과 후보 구성

- [Vercel Functions](https://vercel.com/docs/functions/limitations): Hobby 함수는 최대 300초. 연결 준비·5분 통화·종료 확인을 단일 호출에 담을 여유가 없다.
- [Supabase Edge Functions](https://supabase.com/docs/guides/functions/limits): Free 실행 시간은 150초. 여기도 5분 감시를 한 호출로 처리할 수 없다.
- [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart): 초 단위 주기와 pg_net을 통한 HTTP 호출을 지원한다. 현재 DB에도 두 확장이 설치돼 있다.
- [GPT-Live 서버 제어](https://developers.openai.com/api/docs/guides/voice-server-controls): 기존 WebRTC 세션에 서버 sideband를 연결하고 `session.close`를 보낼 수 있다. `session.closed` 수신을 종료 확인으로 삼는다.
- REST hangup은 상세 레퍼런스에 SIP용으로 설명되어 있어 WebRTC 종료 수단으로 가정하지 않는다. 세션 응답의 `expires_at`도 임의로 정할 수 있는 시작 옵션으로 확인되지 않았다.

추가 서버 없이 검토할 후보는 **Supabase DB에 통화·종료 기한·작업 소유권을 저장하고, Supabase Cron이 짧은 Vercel 감시 작업을 이어 실행하는 방식**이다. 아래 시간은 설계 제안이며 실측값이 아니다.

1. 통화 생성 전에 계정당 활성 통화 1개와 사용 가능 시간을 원자적으로 확보한다. 마이크를 눌러 시작한 연결부터 통화 중 대기 시간을 포함한다. 홈 사전 연결은 제거한다.
2. Vercel 감시 작업은 공급자의 sideband를 연결해 시작·사용량·종료 이벤트를 관측한다. 한 작업의 감시 구간은 45초이며, 종료 확인·DB 기록 여유를 포함한 함수 최대 실행 시간은 90초다.
3. 다음 작업은 이전 작업이 끝나기 전에 준비하고 소유권을 넘긴다. 종료 기한을 맡은 작업이 서버 타이머로 `session.close`를 보낸다. 브라우저 타이머가 종료의 유일한 근거가 되어서는 안 된다.
4. Supabase Cron은 10초 주기로 살아 있는 감시 작업이 없는 통화를 복구한다. 활성 통화가 없으면 외부 HTTP 요청을 만들지 않는다. 작업 토큰은 짧은 유효기간·통화 범위로 제한한다.
5. 공급자가 종료를 확인한 뒤 실제 연결 시간을 정산한다. 확인되지 않은 통화를 단순 만료로 해제해 두 번째 통화를 허용하지 않는다.

**보장 범위 주의:** Cron만으로 매번 정확히 300초에 끝난다고 볼 수 없다. 작업 시작 지연·콜드 스타트·작업 중단·공급자 장애가 있으면 늦게 종료될 수 있다. 다음 감시 작업의 준비와 복구를 실제 호스팅 환경에서 검증하고, 지연을 측정해야 한다. 허용할 수 없는 지연이 확인되면 정책이나 실행 구성을 사용자와 다시 결정한다. 브라우저 종료만 구현한 상태를 서버 강제 종료라고 표시하지 않는다.

## 실제 공급자 시험

재현 도구는 `scripts/probe-live-server-control.mjs`와 `scripts/probe-live-webrtc-client.mjs`다. 명시적인 `--live` 옵션이 있어야 호출하고, loopback에서 실행당 세션을 한 번만 만든다. 네이티브 Node WebRTC가 합성 무음 트랙을 전송한다. 실제 마이크·회원 계정·대화 원문은 사용하지 않았다. 모델 `gpt-live-1`, 음성 `noeul`을 유지했다.

| 시험 | 감시 연결 교체 | 서버 종료 요청 시점 | 종료 확인 시점 | 요청→확인 | 공급자 최종 usage.seconds |
| --- | --- | ---: | ---: | ---: | ---: |
| 재연결 | 기존 연결 해제 후 새 연결, 2차례 | 25.007초 | 26.183초 | 1.176초 | 23 |
| 겹친 인계 | 새 연결 확인 후 기존 연결 해제, 2차례 | 25.003초 | 25.926초 | 0.923초 | 23 |

시점은 서버가 시작 이벤트를 관측한 뒤의 경과 시간이다. 두 시험 모두 서버가 `session.close`를 보냈고, 마지막 감시 연결과 WebRTC 클라이언트에서 `session.closed`를 받았다. 종료 이유는 `close_requested`다. 클라이언트는 종료 명령을 보내지 않았다. 시험 종료 후 WebRTC 트랙·연결·로컬 서버를 정리했다.

- 증거: [재연결](evidence/voice-sideband-reconnect-20261128.json), [겹친 인계](evidence/voice-sideband-overlap-20261128.json).
- 두 통화의 공급자 보고 사용량은 합계 46초다. 서버 관측 시간과 공급자 사용량은 동일하지 않으며, 청구서의 실제 지출액을 조회한 결과가 아니다.
- 25초는 기능 시험값이다. 제품의 5분 정책을 바꾸지 않았다.
- 이 결과는 **로컬 서버에서 실제 공급자 제어 성공**이다. Vercel·Supabase에서 5분 통화를 이어 감시하거나 실제 브라우저가 닫힌 상황을 검증한 결과는 아니다.

## 구현 상태

- `0031_voice_usage_ledger.sql`: KST 사용량·동시 통화 잠금·종료 요청/확정 분리. 불확실한 생성·종료는 자동 해제하지 않는다.
- `0032_voice_watch_jobs.sql`: 일회용 작업 토큰, 45초 작업, 연결 확인 heartbeat, 후속 작업 연결 확인 후 인계, 공급자 종료 확인 후 멱등 정산. 제공자 보고 사용량은 별도 보관한다.
- `0033_voice_watch_dispatch_cron.sql`: 10초 주기 예약 실행·초기 감시 발급·초기 연결 확인. 기본 비활성이므로 외부 HTTP 요청을 만들지 않는다. 기존 cron은 수정하지 않는다.
- `/api/internal/voice-watch`: `VOICE_WATCH_ENABLED=true`일 때만 동작한다. 종료 기한은 DB 시각 차이에 따르며 claim 요청 왕복 시간 전체를 보수적으로 뺀다. DB 장애·인계 실패 시 먼저 종료를 요청하고, 종료 확인 없는 잠금은 유지한다. 대화 원문·오디오를 저장하거나 로그로 남기지 않는다.
- DB/서버 집중 테스트 15개와 전체 테스트 478개 통과. lint·프로덕션 build 통과. 실제 DB 적용과 제품 `/api/live` 연결은 아직 하지 않았다.

## 배포 환경 검증 순서

1. 개발 Supabase 권한으로 실제 기존 스키마를 비교하고 0031–0033을 적용한다. 서비스 운영 DB에는 적용하지 않는다. 기본 비활성 상태를 확인한다.
2. 개발용 Vercel 미리보기에 감시 endpoint를 배포한다. 동일 OpenAI 프로젝트의 서버 키와 개발 Supabase 연결을 확인한다. endpoint 접근 보호가 pg_net 요청을 막는 경우 보호 우회 비밀값을 안전하게 설정하거나 별도 검증용 개발 주소를 사용한다.
3. 실제 사용자의 통화 대신 테스트 레코드와 합성 무음으로 초기 감시 연결·인계·수동 종료·실패 복구를 검증한다. 처음에는 짧은 종료 기한을 사용하고, 통화가 살아 있는 상태에서 작업을 제거하거나 설정을 끄지 않는다.
4. 5분 경계, 남은 일·월 시간이 더 짧은 통화, 탭 종료·백그라운드, 감시 작업 실패·재실행을 검증한다. 종료 요청과 확인 지연을 각각 측정한다.
5. 검증한 뒤 계정별 예약·세션 생성·초기 watcher 준비 확인을 `/api/live`에 연결한다. 준비되지 않으면 SDP를 넘기지 않고 서버에서 세션을 닫는다. 생성 응답 유실은 자동 해제하지 않고 운영 복구 대상으로 둔다.
6. 수동 종료 API·위임/맥락 호출의 활성 통화 확인·남은 시간 UI를 연결한다. 음성 시간 정책 적용 전까지 기존 보호 한도는 유지한다.

## 배포/복구 조건

감시 코드와 DB 함수만 존재하는 것으로 한도가 적용되지는 않는다. Supabase 연결 후 개발 DB에 0031–0033 및 0035를 적용했다. 운영 DB는 변경하지 않았다. 실패한 첫 호스팅 시험을 종료한 뒤 dispatch는 다시 비활성화했다. 실제 제품 통화 API 연결은 미완료다.

활성 통화가 남은 상태에서 `VOICE_WATCH_ENABLED`나 dispatch를 끄면 서버 종료가 중단된다. 되돌릴 때는 **새 통화 발급 중지 → 기존 통화의 공급자 종료 확인 → 활성 레코드 0 확인 → 감시/예약 실행 비활성화** 순서를 따른다. ack를 놓친 통화는 실제 공급자 종료 증거 없이 임의 해제하지 않는다. 생성 응답 유실과 종료 이벤트 재생 범위를 놓친 작업은 수동 확인이 필요할 수 있다.


## 개발 호스팅 후속 검증 — 2026-11-28

- 최신 `dev`의 암호화·Runyour 임베딩 전환·사전 연결 제거를 작업 브랜치에 병합했다. `0030_field_encryption.sql`과 번호 충돌을 피하려고 미적용 텍스트 마이그레이션을 `0034_text_usage_quota.sql`로 변경했다. 병합 후 전체 테스트 504개 통과.
- 개발 DB `here-dev`에 0031·0032·0033·0035 적용. 기존 6개 cron은 그대로 두고 `here-voice-watch`만 추가했다. 서버 예약 발급용 authority는 아직 미설정이며 제품 통화는 새 원장에 연결되지 않는다.
- 첫 Preview `here-2x7uhmlny-here23.vercel.app`에 배포 단위로 `VOICE_WATCH_ENABLED=true`를 설정했다. 기존 dev/production 환경변수는 바꾸지 않았다.
- Vercel 로그인 보호를 해제하지 않았다. 기존 자동화 인증값을 Supabase Vault에 저장하고 config에는 secret ID만 저장한다. 0035는 예약 요청에 이 인증 헤더를 붙인다. 일반 사용자/익명은 config·Vault·헤더 생성 함수에 접근할 수 없다.
- Supabase→보호된 Vercel→Supabase 사전 시험 HTTP 200, `processed:false` 확인. 무효 토큰이므로 공급자 호출은 없었다.
- 17:56 KST 합성 통화: DB 작업 발급·claim 성공, Vercel 감시 연결은 실패. 기존 로컬 관측 연결로 32.054초에 안전 종료 요청, 32.820초에 공급자 종료 확인. 공급자 보고 31초. **호스팅 종료 성공이 아니다.** 증거: `evidence/voice-hosted-local-rescue-20261128.json`.
- 테스트 원장의 시작은 통화 생성 후 DB 레코드 삽입 시각이므로 원장 구간 27.454984초와 공급자 31초가 다르다. 이 수치는 실제 제품 시작 시각 집계 검증으로 사용하지 않는다.
- 해당 임시 통화만 로컬의 종료 확인 증거로 닫고 dispatch를 껐다. 실패 단계·HTTP 상태 코드만 남기는 진단을 추가했고, 유료 통화를 더 열기 전에 비과금 연결 진단을 진행한다.
- DB advisory에서 새 테이블의 RLS 정책 없음은 직접 접근을 전부 차단하는 의도된 구조다. SECURITY DEFINER 함수 공개 실행 경고는 서버가 보관하는 통화별/단기 작업 capability 검증이 적용되는 경로다. [Supabase 점검 기준](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable).


### 재개 후 검증 기록 (2026-11-28)

- Vercel 연결 실패 원인은 OpenAI 환경변수 끝의 줄바꿈이었다. Authorization 헤더 생성 시 TypeError를 확인하고 읽을 때 trim하도록 수정했다. 기존 키 자체는 수정하지 않았다.
- 45초 감시 요청이 pg_net의 다음 요청을 대기시키는 실측을 확인했다. 감시 API는 claim 후 202로 응답하고 Next.js `after`로 최대 90초 실행 구간 안에서 감시를 이어간다. DB heartbeat와 cron 복구는 유지한다.
- 개발 DB의 60초 기한에서 후속 연결 인계와 서버 종료를 확인했다. DB 관측 시간 60.695791초, 기한 초과 0.695791초, 공급자 보고 69초. 로컬 관측 연결은 종료 명령을 보내지 않았다. DB 레코드를 연결 후 넣었으므로 이번 DB 구간을 공급자 과금 구간의 측정으로 해석하지 않는다.
- 0034 텍스트 한도와 0036 API 제어를 개발 DB에 적용했다. 제품 음성 API는 예약→공급자 생성→감시 연결 확인→SDP 반환 순서다. 준비 실패는 종료 확인 후에만 정산하며 불확실한 상태는 잠금을 유지한다.
- 수동 종료 API, 음성 위임·맥락 API의 본인/활성 통화 확인, 클라이언트 취소·기한의 보조 종료, 메뉴 일·월 남은 시간을 구현했다. 브라우저 조작 검증은 CUA 연결 타임아웃으로 미실시다.
